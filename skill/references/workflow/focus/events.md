# 事件工作卡

`event_topology`。需要确定一个动作会产生哪些事件、何时出伤或什么条件会触发时读这张卡。

1. 沿实际动作查技能、天赋、命座、武器、套装和共鸣。列出会改变本次结果的命中、附着、Buff、状态及资源。逐项区分普通伤害、同一组件的替换、独立追加。多个组件需要独立取样、触发或改变状态时，按各自实际时点与稳定 ID 表达。
2. 对持续效果核对首次发生、间隔、末次边界、暂停、刷新和离场。后台少一跳或刷新时点有争议时，按[排轴资料索引](../../data/combat-references.md)查具体攻击通道。施放占用结束后，符合条件的后台效果按自身时钟继续。改变下一轮时间后重新核对旧实例何时结束。快帧条件下另查[计时器影响范围](../../data/frame-rate-timing.md#逐计时器查证)。
3. 分开核对伤害命中、附着许可、实际反应和领域计层。涉及动态领域时按[元素](../../app-mechanics/elements/runtime.md)和[特殊反应](../../app-mechanics/elements/special-reactions.md)填真实初态、附着档案、共享计时与绑定。直伤使用当击对应的最近完成结算。用户要求逐组满足条件时，每组分别核对实际流水。

已有来源和输入可直接使用。辅助拓扑用于盘点，需要时从 `capability_index` 的 `/event_topology` 查合同。读取 `event_topology` 的指针相对资源根，修改完整候选时的根为 `/extensions/event_topology`。`gs_validate_topology` 核对已写的引用、调度及覆盖声明。采用强类型材料化时使用其[执行绑定](../../app-mechanics/execution/materialization.md)，之后还要在实际结果中核命中、资源和收益。角色机制未知时按[数据库说明](../../data/database-readme.md)定向找资料，保留待核项并继续可做的部分。例子见[来源与结果对照](../coverage-and-review.md)。

回能依赖反应时，先查[真实反应触发的直接回能](../../app-mechanics/execution/resources-and-lifecycle.md#真实反应触发的直接回能)，以实际反应和到账流水核对触发。确认有条件的回能再写入资源账。

用户要求“每组至少一次”时，先按动作组保留这个要求；不能用全轴总次数代替。动态机制的初态、先后依赖和实际触发未建立时，别用常量填满效果后称为动态验证。先讲清要发生什么，再沿[任务与来源对照](../task-evidence.md)保存必要的条件与采用位置。
