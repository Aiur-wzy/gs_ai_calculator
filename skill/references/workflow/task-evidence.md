# 把原题、游戏解释和实际结果对起来

在任务有多个条件、续轮、反应或动态收益时读取。目的是避免“算通了一份输入，却没完成原题”，不是增加必须填完的表格或新的计算门。简单问答直接回答；已有正确输入直接复用。

## 先保住用户真正要的东西

保留原题原文及后续裁决，再用自己的话列出会影响交付的要求。比如“每组攻击至少一次扩冰”是逐组要求，不能改成“全轴有一次扩冰”；“验证两轮”不能改成“证明无限循环”；“动态层数”不能因为静态值能算通就悄悄替换。术语不清时先回到原话和上下文，不以报错或自己的摘要代替用户目标。

工作记录可以用普通小文档，也可以用现有 App 服务。两者都不是另一套轴或授权凭据：

- 原生：`gs_record_finding` 接收一个 `record` 或一组 `records`，二选一。`gs_read_context` 的 `resource="task_evidence"` 返回目前已记录要求与当前输入的对照。
- 独立 CLI：`workflow init --plan plan.json --audit audit.json` 建立工作记录；`workflow workspace --plan plan.json --audit audit.json` 查看对照，更新请求通过该命令的 `--request` 传入。以本次 capabilities 中的完整合同为准。
- 记录类型包括原题 `task_source`、要求 `requirement`、资料解释 `source_note` 和观察 `observation`。每项保留 `id/type/description`；需要时加 `source_refs`、`input_refs`、`adopted_refs`。先用最少的记录保存关键判断，不为记账反复重发已成功的操作。

一条原生记录的形状示例：

```json
{"record":{"id":"task.req.second_round","type":"requirement","description":"按原题完成第二轮所有爆发，并检查每次释放前的能量","disposition":"pending"}}
```

`pending` 是待处理，`not_implemented` 是尚未实现；`not_applicable` 要有本场景不适用的依据，`implemented_elsewhere` 要指出实际位置。用户明确不计才使用 `user_excluded`，它仍不是批准凭据。合法近似记 `approximation` 并说明原机制与替代做法。资料查到、已经录入、实际执行、完成验证是不同事实；把状态改成 adopted 不会替你完成任何计算。

## 阅读时留住会改变计算的条件

一个来源可以包含多项效果。原文与参数留在同一份资料中，自己的解释另写，不把摘要覆盖原文。拿到命座、精炼或套装条目后，先辨清“由谁触发、给谁、何时、作用于哪类伤害、什么时候取属性、如何刷新”。再决定用什么输入表达。不要只摘一个倍率或一句“全队增伤”。

`gs_query_context` 等读取若返回 `notebook_ref`，可按该引用读取无损资料小档；其 `raw` 保存实际返回内容，`interpretation` 只是可编辑解释骨架。空字符串索引不证明没有被动，附录目录也不证明正文已读。分别核身份、命座、精炼等级、参数单位与术语的实际出处。正文被分页时沿真实续读位置完成当前所需部分。

例如“造成反应后给其他队友的某类伤害增益”：不能只因为提供者也在队伍里就给自己，也不能只因两个伤害名字相近就共享增益。先建立真实触发和受益范围，再看结果中的命中和所取属性。静态面板已有的常驻收益不再额外加一遍；战斗条件收益不能为了省事全折成开场常量。

按因果拆开理解：施放或已有状态 → 命中/接触 → 能否附着与实际反应 → 后续状态、资源和收益 → 本次取样与伤害 → 刷新/到期。具体游戏效果可能在不同节点取值，不能把这张理解顺序当成所有公式的强制执行顺序。例如后台效果在退出后仍每隔一段时间命中，应由独立周期继续产生事件；反例是把全部出伤时间记为施放占用，让角色一直不能切出。原文规定“替换原命中”时只保留转化后的那一次交付；“另外造成一次”才建立独立追加事件。

## 修改后检查变化，而不是从头重读

改时点后看附着、接球、持续效果和取样；改配装后看相关基础值、属性转换、来源绑定与能量。资料版本没变无需反复全量查询。App 会提示已记录引用失效或输入改变；这表示需要复核，不证明游戏条件必然错误。修正解释时用 `supersedes` 指向旧记录，保留改口原因。

优先解决会影响后继判断的真实问题：格式/来源绑定未过时不能据此断言能量不够；未写回能时不能断言配装无解；某类伤害没有事件时不能把“未观察”写成“该收益不适用”。有限轴逐次能量与可选稳态结果分别解释。

## 一次交付前的最后对照

回到用户原话，查看当前输入和实际结果是否能回答每项关键要求。重点复核已知容易漏的条件、当前改动以及首次/刷新/末次/跨轮边界；不用机械重复每次操作。结果 `accepted` 只说明当前输入通过，不能证明未知角色机制已自动补齐。空的差异列表也只代表已记录项目没有差异。

能在授权范围内查资料、补输入、改词条或改时点的就继续做，不把这些工作说成“等用户审核”。确实要改用户锁定项、纠正数据库既有事实或同步正式白板时，按真实批准流程提出具体方案。最终先用普通玩家的语言说明：算到了哪一步，哪些效果算入，哪些采用近似或仍有出入，结果是否能用，需要用户在哪个页面做什么。技术编号和内部状态放在后面的证据说明。

原生 DSH 与安装了可选扩展的官方 DSH CLI 可在本轮结束前收到一次具体差异提醒；它不替模型决定机制，不强制续跑，不重开已结束目标。普通 CLI 没有自动收尾钩子，主动查看同一份对照即可。没装插件、没填工作记录或辅助读取失败都不取消正常计算能力。
