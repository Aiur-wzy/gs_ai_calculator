# 接续用户创作白板与App聊天

收到`genshin-whiteboard`、白板交接包或进入App聊天时读取本节。白板保存成功不代表机制完整或轴已可执行，不能直接送入伤害引擎；先读取当前能力契约。

## 修改范围

默认保留已有角色、等级、命座、面板、装备、轴长、动作、变体、顺序和时点。用户要求调整时，在其授权范围内修改候选。只锁动作顺序的自主排轴可优化未锁时点。仅要求检查漏算时，保持已有配装和动作安排，修正计算输入。范围不明确时先完成独立可做的工作，再就必要的差异询问。见[工作法](index.md#遇到失败怎样继续)。

这是Agent的行为规则，不要求代码用关键词或权限开关判断用户授权。`build`和`calculate`区分输出形态，不区分角色/动作的修改权限。所有修改先形成可审核候选，不声称已改用户原文件；结束时说明实际修改及原因。未经授权的轴调整仅列为建议。数据格式、稳定文档身份、版本线、数据库快照、候选一致性及防覆盖检查仍须通过，不能改身份绕过检查。

## 从空白板逐步构建

当前原生流程使用`workflow=artifact`，按实际能力读取候选摘要、`candidate_board`和白板schema；旧build只用于其明确旧环境。允许空队伍、只有角色、没有动作或面板未填；用户只要求加角色，就交付角色草稿，不强迫补动作或立即计算。

1. 用`gs_search_catalog`按中文名查角色、武器和套装，再用`gs_query_context`读取真实ID对应原文。详细结果保存为可重读resource，沿用分实体缓存，不反复查库或猜ID。
2. 用`gs_add_character`加角色，`gs_patch_whiteboard`改装备、面板与动作；基础属性由数据库按等级与武器读取，必要时用`gs_character_panel_basis`核对。角色默认90级、0命须说明，用户指定优先。
3. 基础白值不等于成品面板。未知成品面板保持null，不能填0或从基础值虚构；用户给定面板已包含武器和套装常驻属性，不要求五件圣遗物词条。
4. 每轮读取当前修订再写候选，结束时说明变更、默认值与未填项。审核应用后可在同一聊天继续；未应用时仍可完善候选。草稿不代表已计算，不能编造DPS；白板可逐步准备原生计算表示（artifact工作流），不要求先选满角色或先添加动作才能和Agent继续。

## 完善排轴与计算

使用[工作卡](index.md#五张工作卡)和[按需披露](context-use.md)组织资料。身份、配装、动作、事件和数值可交错补齐，未完成的候选也可保存。需要自主排轴时主动核对占用、空档及收益，修改后用当前输入重算。

白板有角色和动作后，可用`gs_transition_phase(prepare_calculation=true)`转换原生表示，也可沿[共用输入编辑](../app-mechanics/input-editing.md)直接导入原生输入；target_phase只设置阅读重点。盘点技能、天赋、命座、装备及持续状态造成的命中、附着、Buff、资源、有限多段和后台周期，将采用知识材料化为通用执行输入。辅助拓扑／预期清单不作为强制计算前置项；实际消费的强类型材料化、覆盖及其绑定仍必须完整。初编辑不以循环为门，正式结果要求真实动作、能量、通用元素、数值与执行绑定通过。

`gs_read_context(resource="candidate_board")`读取候选白板视图。尚未转换时白板是主要输入；原生表示中，获授权变更角色／面板／动作只修改原生主要字段，由共用服务重新生成白板与映射，不手工同步两组时点。高级规则、属性、周期、材料化等保留在完整原生输入，不能因简化白板无法展示而删除。缺模型时按真实合同补必要部分，不重建已有动作。

新增攻击动作填写真实能力及动作ID；可投影内容由App映射到候选白板。切人／等待仍有自己的稳定ID，不因数组位置相同便当成攻击动作；只移动辅助切人不要求同时移动不相干的用户动作。切换的白板视图表示切入对象，原生能力执行者与`switch_to`仍按真实合同填写。相对动作的延迟由已有调度重算，绝对时点不由App猜测平移。未知变体、面板和机制保留待核，不填零CD、零能耗或虚构倍率来消除pending。

正式结果必须同时保留`character_semantics=agent_declared`、事件盘点、数值与绑定验证和通用引擎验证状态。App逐项核对候选白板与实际计算输入一致，确认后一起应用白板与结果；界面外另行编辑导致冲突时以当前文档新建任务，不通过伪造回执覆盖。

### 动作接纳 v3 意图

当白板能力提供 `action_admission_intents` 时，一个元素爆发动作最多由一条意图拥有。初编辑允许意图的`context`与`initial_ready_in`保持`null`，不能因此拒绝白板保存或动作录入。需要计算时按需完整分页读取相关目录并执行2A分组，只从已审核完全/部分匹配组选择精确`model_ref`；目录卡片不含执行权。只有用户显式点击普通开放世界预设，才同时写入固定`static-action-admission-context-v1`场景和`initial_ready_in=[]`；Agent不根据“通常开场就绪”自行补值。

handoff只传播intent及未确认proposal，不生成`accepted_fingerprint`或私有marker。场景或初始队列仍为`null`只会阻止相关正式计算接纳，不应阻止编辑／保存草稿。完整结果回流须逐项闭合intent → 白板动作 → 原生动作/能力 → 唯一来源 → ready静态编译 → 运行时committed回执。修改角色、技能、动作、variant、场景或初始队列后清除旧确认并重新fresh preview。

## 文件交接与工具边界

白板的外部文件交接入口输出文件和说明。App 内继续任务时，使用「AI 助手」打开当前会话。CLI 为 `whiteboard new --output`、`whiteboard validate --input`、`whiteboard handoff --input --output-dir` 和 `whiteboard result --input --result`。交接目录含 `whiteboard.json`、`native.pending.plan.json` 和 `交给Agent.md`；在副本上工作。

正式回流使用真实`calculated.json`，不能用单独result.json冒充。未改白板时按原文件校验；获授权改动时一起交付当前候选输入及对应计算包。通过共用编辑入口修改原生文件时，白板与映射同样由App派生，不手算关联指纹。普通独立文件计算不继承另一个会话的领域批准；需批准的消费仍应接入受信服务。

原生领域工具与CLI复用同一输入／计算服务。DSH通用文件、Shell、jobs和子Agent按真实工具与权限使用，不将其误称为额外App批准；没有某工具时如实说明。不要自行读取禁止的往期实验答案或在任务范围外操作其他会话。更换游戏输入会使旧结果失效，效果轴与伤害轴展示计算所得内容。

`save_current`保存正式文档，不是隔离候选。未完成候选可在任务工作目录保存输入文件，或经`export_candidate_input_draft`让用户选路径保存App捕获的快照。分别报告文件实际SHA／可重读状态或操作卡completed；queued／presented不是成功。导入只恢复输入与只读证据，不恢复旧批准、static来源准入或写权；正式审核／同步仍独立进行。

## 向用户交接

首段回答当前问题或当前结果。涉及用户操作时，先按 App 回执核对页面、卡片、按钮和目标，然后说明去哪儿点、点完会发生什么。

| 实际状态 | 告诉用户什么 |
|---|---|
| 正在处理或已留草稿 | 说清已完成的内容、还缺什么、是否继续处理。可编辑的草稿可以看，正式数值需要实际计算接纳。 |
| 已计算，等待同步 | 先说结果是否已接纳、白板是否已更新。当前会话有可审核候选时，请用户在当前对话顶部点「审核候选」，查看变化后点「同意并同步」。同步后 App 打开正式白板。无需先请求跳转报告的操作卡。 |
| 等待保存 | 说清要保存候选输入、正式白板还是完整计算包。指出当前会话中的具体文件卡和可见操作，完成选址后仍需等待实际写入回执。 |
| 已同步、尚未另存 | 说结果已出现在哪个正式文档，用户需要本地文件时从相应保存入口选择路径。 |
| 已实际保存 | 说明写出的文件名称、位置及其内容。只有能按回执确认后才用「已保存」。 |
| 操作失败或结果待核对 | 说清影响哪一步及现有内容是否可用。按 App 指示去对应卡片核对；写入状态未知时先查现状。 |
