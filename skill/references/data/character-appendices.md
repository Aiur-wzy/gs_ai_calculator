# 角色动作资料附录

## 默认读取：先发现正文，再决定采用

涉及角色机制、配装、排轴或计算的新任务，角色确定后默认读取该角色全部可读的approved／pending附录。这里指数据库正文，不是只打开本说明、取得分类计数或保存资源引用；一般软件操作／闲聊不启动这套资料流程。其他技能原文、倍率、装备、高级配置和网络资料按当前依赖查询，计算必需事实仍须有依据。

1. 当前工具目录提供`gs_get_character_appendix_index`时，以`{db_character_id:实际角色ID}`读取窄只读导航。版本线与DB身份沿用会话，不自填。默认回执给出非空分类摘要及`resource`、`pointer`、`next_offset`；需要完整目标／未解析范围时沿`targets_ref`／`issues_ref`，用`gs_read_context`分页读取。详情与边界按需读`gs_read_context(resource="appendix_navigation_capabilities")`，不在此复制字段表。索引complete只证明约定范围枚举完成；`body_read=false`、`execution_authority=none`，不证明正文已读、知识适用或机制可执行。
2. 正文继续用`gs_query_appendix`按真实`target_type`、`target_id`、`category`、`version_line`与`status`分别查询，approved和pending各分类、各页读完。单页最多10条；按真实分页字段继续，不能只读第一页。聚合中已实际读完、同版本同状态的approved正文可复用，不再重复查询。
3. 没有上述导航时，用实际角色查询的字段定位目标，逐目标用`gs_list_appendix_categories`发现approved／pending分类，再读正文。`character.id`→character，`skills[].id`→skill，`skills[].proud_skill_group_id`→skill_param，`talents[].id`→talent；`extra_info`中`info_type=sub_skill`的`source_id`→skill，实际`proud_skill_group_id`→skill_param，`info_type=inherent_skill`的同一参数组ID亦定位inherent_skill。只用返回的真实ID／类型，不猜名称、数组下标或ID模式。公开角色详情没有`related_targets`字段，不要求调用数据库内部函数。
4. 角色本体分类为空或聚合`annotations=[]`，不代表技能、附属技能、参数组、固有天赋及命座没有pending。查询失败、缺目标ID或索引partial分别记录范围，定向补查；不能用全零或“无附录”掩盖工具故障。真实无条目时保留空查询事实并正常继续。
5. 同快照已读正文按角色小资源复用，记录事实／来源ID、状态、版本、采用／不适用／冲突／待核及执行输入引用。新增角色补读；资料版本或内容变化后复核受影响范围。DSH压缩／恢复先取小索引，精确正文不在可用上下文时定向补读，不为每条消息重查全队，也不建立App已读权限状态。

未拥有命座或当前不适用内容读后可不采用。pending保持知识候选身份；App的verified只证明资源、指纹和归属，不证明公共审核通过。核实来源支持的事实后按当前强类型合同材料化；独立核实资料另记真实证据，不能把原pending改名为agent_research绕过来源校验，也不要求先将公共条目升为approved才能做合法场景输入。approved知识同样没有直接执行权。

涉及角色的替代资源、实体转换或重施效果时，沿技能或固有天赋归属读取附录。记录事实适用范围、实际来源与相关执行输入。资源消费、替换实体和刷新状态分别核对；附录确认了其中一项时，其余时序和数值仍按各自证据核实。可用输入见[星月适配](../app-mechanics/elements/special-reactions.md#月绽放草露转换核及消费收益)和[资源与生命周期](../app-mechanics/execution/resources-and-lifecycle.md)。

优先复用当前会话可读的正文资源。实际目录提供文件、Shell 或 CLI 且权限允许时，可在任务目录保存原文、来源和采用摘要，也可用公开 HTTP／annotations 等只读入口完成同一范围。资料有下一页或引用时沿实际入口继续，确实读不到的范围如实记录。对影响计算的未知按[恢复路线](../workflow/index.md#遇到失败怎样继续)补源；其他可独立完成的编辑、保存、研究和问答继续做。文件与 Shell 权限和候选同步、公共事实审批分别核对。

## 发现新资料后的维护

实验中明确查证、值得复用的角色资料应形成角色级知识提案，不应永久只留在报告、队伍名或单个方案里。只要答案能够定位到明确角色以及该角色的技能、天赋、命座或实际攻击／效果分量，并有可复核来源，就建立数据库 **appendix candidate**。候选的事实身份始终是角色侧实体与组件；队伍、轴、敌人和本次计算只负责引用这些事实，不能进入事实身份。候选用于后续复用和审核，不自动取得引擎执行权。这里“建立数据库候选”指形成库外知识提案，经来源/内容审查、用户同意、隔离候选构建和完整新DB发布后才入库；不是让普通Agent直接写活动数据库。当前无提案写工具时先保留会话finding/来源引用，按实际文件权限交付，不能伪造已写入公共库。

## 何时写入

资料阶段出现以下任一类明确结论时，在本轮交付前保留可供维护的来源/提案记录；实际数据库发布不作为该次计算完成的前提：

- 动作施放、占用、前后摇、可取消点或多段续段窗口；
- 单次动作的攻击分量、命中次数、命中偏移或持续命中频率；
- 周期来源的首击、间隔、次数、持续、结束、切人及替换／刷新语义；
- 每个实际分量的元素、GU、是否尝试附着、ICD counter 与规则组；
- 后台攻击、召唤物、命座追加攻击等与父动作、生命周期的关系；
- 技能派生的染色／元素转化、快照、领域和状态规则，以及固有天赋或命座对这些组件的修改；
- App 建立该角色时必须询问或填入的角色侧选项，例如命座、技能变体、染色元素及启用的天赋效果。

只有“查到页面”或“实验结果看起来符合”不够。若资料只能支持其中一部分，只写该原子事实，其余字段保持未知。伤害总数、反应次数、旧方案手填事件和 Agent 排出的时点只能帮助定位待查项，不能反向证明动作机制。

## 候选记录

每条候选至少保存：

1. `version_line`、角色 ID，以及事实实际归属的技能仓／技能／天赋／命座／组件、槽位、变体、连段阶段及适用命座／有效等级；
2. 单一事实类别与结论，包括时间基准、单位和适用条件；
3. 对动作、命中、周期、附着或生命周期中哪些字段有证据，哪些仍未知；
4. 来源标题、稳定网址或固定提交、资料版本／日期、检索日期及支持结论的精确定位；
5. 与本地原文、攻击候选或既有注释的对应身份和指纹；
6. `status=pending`、待审原因、后续核实项，以及 `execution_authority=none`。

一条候选只陈述来源真正支持的事实。不同来源、不同技能分量或互相冲突的说法分条保存，不用折中值合并。社区实测可作为有版本的实验依据，但不能标成游戏源码；测试服、旧版本和当前版本分开。角色同名、技能同名与不同形态使用原始 ID 消歧。事实 ID、标题和去重键不得包含队伍名、benchmark ID、动作轴 revision 或队友；同一角色的同一事实只保存一次，任何队伍都引用这一份。命座、天赋或装备改变角色自身行为时以适用条件或独立角色组件表达，不复制成某队专用事实。

当前服务按事实实际归属挂载知识，使用`skill`、`talent`、`inherent_skill`等真实角色侧目标，读取流程统一见上节。内容写明真实角色和组件，不以队伍作为事实身份。首批来源包为`src/genshin_db/resources/mechanics/character-action-appendices-v1.json`；角色填入模板、场景绑定和历史导入回执位于`benchmarks/followup/character-action-appendices-v1/`。源包不随普通数据库查询重播种，修订先形成精确内容提案，再经同意、隔离候选和完整DB版本发布，不能直接补活动库。

## 角色级 App 填入模板

每个角色只维护一个与队伍无关的结构化目录条目，目录内可按动作或组件保存多份小型 **App 填入模板**。模板引用候选的稳定 ID，用于告诉 Agent/App 建立该角色时要填哪些入口、呈现哪些选择和检查哪些派生组件；它不是机制正文，也没有执行权。模板至少写明：

- 角色 ID、模板 revision、适用版本、技能等级和命座条件；
- 可填动作、变体、连段阶段、实际攻击／效果组件及父子关系；
- 染色、元素转化、周期来源、附着、快照、领域等角色侧选择和派生提示；
- 固有天赋、命座和该角色自身装备效果对组件的修改，以及必须由用户或 Agent 明确选择的条件；
- 可生成的动作档案、周期通道、附着适配和审计键，以及仍待核实或需要手工补充的字段。

跨多个动作触发的固有天赋或角色状态必须放在角色目录的 **character overlay**，由各动作模板引用；不得因为首次实验只用了某个技能，就把角色级机制挂死在该技能模板下。overlay 按实际角色归属事件接收触发输入，动作模板只描述动作本身。例如枫原万叶目录应分别提供 E／下落与 Q 组件，Q 单独接收元素转化／染色；A4 由 E、乱岚拨止、Q 等任一万叶归属的实际扩散事件共同引用，二命领域元素精通仍作为 Q 的命座覆盖层。染色不能代替扩散证明。

模板不能写“神鹤万心中的万叶”或预填某个队伍的染色答案；具体 benchmark 只选择万叶模板、命座和本场景染色，并绑定到动作检查点。

角色模板是可复用填入契约，不得包含队友、队伍动作序列、轴内绝对时间、敌人初始元素底、整队 Buff 取舍、目标总伤或本场景期望反应。不得把角色专用 JSON 片段写进 App 通用提示、通用算法分支或引擎默认值；需要推广时先抽象通用合同，再由数据库资料选择和参数化。同一角色、同一条件的模板只保存一次，重复出现在多个队伍时不得复制。

## 与 benchmark 场景绑定分离

benchmark 或实验 manifest 只保存**场景绑定索引**：引用哪些角色模板及其 revision、填写该场景专有的角色侧输入，并链接现有 benchmark 合同或 fixture 中的命座／装备／等级、动作检查点与时点、敌人与场景开关、候选取舍和核对证据；不在本 manifest 复制完整方案。若案例尚无正向动作检查点和事件拓扑方案，必须在 `evidence_gaps` 明示。场景绑定不重新描述角色机制，也不成为通用角色模板；相同角色在不同队伍中只增加新的场景引用。

manifest 只把已经逐事实复核的角色模板或局部正向 fixture 列为支撑证据。已知错误、撤销或条件不完整的旧方案只登记为 `negative_regression`，用于证明新结果不会重现旧错；不得从其中抽取“看似合理”的时点或事件回填候选。当前神鹤万心 stable-facts 中已有的 12 条 approved 基础事实继续保留，新 appendix 只补角色侧动作时序、命中／频率、ICD、天赋／命座组件与生命周期等缺项，全部先以 pending 进入审核队列。

## 审核与提升

候选审核至少检查身份、来源、版本、原文／实测范围、时间基准、分量完整性、ICD 共享关系以及正反例。审核通过后可以把注释提升为 approved，但 **approved 注释仍不是可执行动作派发档案**。只有另行满足[受审动作派发档案](../app-mechanics/actions/dispatch.md)的完整选择器、dispatch／timing／damage／application 证据、fresh 来源核对和原生无损物化要求，才能生成或提升 reviewed profile。

实验可在明确标注的条件下引用 pending 候选建立可复用手工档案；报告必须把 `reusable_plan_profile`、逐实例补充和 reviewed dispatch 分开统计。任何角色事实或模板字段变化都使引用它的场景绑定重新待核，不能从旧计算成功继承审核状态。

## 当前角色资料范围

首批资料来自三组实验，但按角色身份保存，覆盖以下角色：

- 木偶（桑多涅）、奥黛塔、砂糖、阿罗夏；
- 神里绫华、申鹤、枫原万叶、珊瑚宫心海；已有 stable-facts 不重复导入，AYAKA M2／M3／M4 错误方案只作 `negative_regression`；
- 迪卢克、茜特菈莉、班尼特；撤销的 Diluc rev6 只作 `negative_regression`。

枫原万叶虽然出现在两组实验中，仍只建立一组按技能、天赋、命座和真实组件组织的候选，以及一个角色目录条目；目录内的 E／下落和 Q 等模板按组件拆分，A4 作为两个动作模板共同引用的角色级 overlay。不同队伍、装备、轴、染色和敌人状态只在各自 benchmark 场景绑定中引用。旧实验方案、补丁和报告先作为检索索引逐事实复核，禁止整包导入为事实。暂时查不到明确答案的动作继续保留具体工作单，不用近似值填数据库。

当前artifact把五张卡当工作重点，不限制何时查阅或材料化角色资料。导航只整理既有归属与分类，不建立新数据库关系；任何索引都不把pending知识提升为可执行事实。
