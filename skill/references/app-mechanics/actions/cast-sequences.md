# 多段施放与续段窗口

当一个技能由首次施放和若干可续段组成时，先读取每一段对应的数据库条目和 `action_resource_profile.cast_sequence`。同名技能、`subSkills`、短 `cdTime` 或连续动画只能用于发现候选，不能自行推断连段阶段、窗口或冷却语义；没有ready只表示自动来源未获资格，不表示通用续段输入不可用。依据已查证资料/明确假设，可按当前允许的Agent手工合同声明通用cast_sequence；未知字段仍待核，不伪造source_binding或受审档案，不把同名/动画推测当证据。

## 通用契约

引擎能力使用以下字段，不按角色或技能 ID 分支：

```json
{
  "group": "共享连段组",
  "stage": 1,
  "max_stages": 3,
  "continuation_window": 4,
  "cooldown_start": "sequence_start"
}
```

- 第一段保留普通 `cooldown`，从该段 `action_start` 立即进入基础冷却；后续段的 `cooldown` 为 `null`，在同角色、同 `group` 的续段状态内可绕过正在运行的基础冷却。
- `continuation_window` 表示**本段成功后到下一段**的许可窗口；各转段可不同。非末段必须为正数，末段为 `null`。
- 该窗口是下一段允许施放的**最晚期限**，不是最短等待时间。只要动作占用、切人等通用门禁允许，下一段可以立即接续；不能因为窗口是 4 秒而等 4 秒，也不能因为后续 raw `cdTime=2` 而强制等 2 秒。
- 当前引擎合同的窗口按半开区间 `[本段 action_start, 本段 action_start + continuation_window)` 判断；此执行边界不能替代游戏实测的帧级证据；正好落在截止时刻视为过期。为避免帧时点误差，实验轴不要故意卡边界。
- 非末段成功后刷新到下一段的窗口；末段成功后关闭连段。窗口超时只关闭续段许可，不重启、不推迟已经运行的基础冷却。
- 连段阶段不是充能次数或可用次数，不能用 `charges`、`action_capacity` 或多个独立普通技能代替。

当前受审档案还会保留上游各阶段的原始 `cdTime`，用于追溯，不代表后续段各自拥有独立冷却或段间最短等待。执行输入必须遵循 `resource_policy` 与上面的连段契约。动作之间实际出现的间隔应由动作占用、取消窗口、切人等已声明事实解释，不能倒推成续段冷却。

App应用受审档案时，必须同时保存`profile_id`、角色与所选技能/阶段、资料线、快照、上游提交、内容/资源指纹以及首段冷却秒数、次数和恢复策略。首段的`duration/charges/start/recovery`必须与档案完全一致，续段的普通`cooldown`必须为`null`；冲突时拒绝应用，不能只显示提示后继续。当前`verification_mode=saved_metadata_only`只表示保存了可审计的读取结果，动作检查不会fresh重查数据库。数据库更新或资料线变化后应重新读取并应用档案，不能把旧指纹写成当前资料仍批准。

## 资料与动作对账

1. 在资料阶段保存主技能、相关 `subSkills`、受审档案和原文证据；给每段独立能力/动作 ID，并记录共同 `group`、阶段号、窗口和基础冷却所有者。
2. 录入和修改动作时做三方对账：用户给出的动作串、逐项编号的动作表、准备提交给 App 的动作数量必须一一对应。多出的续段、漏掉的续段或把同一段重复计数都需修正相关动作和事件，不要求退回某个focus。
3. 轴长是覆盖预定动作和事件的计算窗口，不是必须填满的目标。不得为了填满题面上限、等待基础冷却或凑完整连段而添加用户未要求的动作或空等。
4. 转换后检查每一段的接纳回执：首段应为 `sequence_start`，后续段应为 `continuation_window`，并同时显示基础冷却 `ready_at` 和下一段截止时点。`pending`、过期、跳段和组不一致不得当作成功。

如果核验后需要改阶段、时点或动作数量，修订action_checkpoint；只修字段映射时保留原动作检查点并记录建模修订。
